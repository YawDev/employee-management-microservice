# employee-management-microservice
Employee Management Microservice built in .NET 9

## Data model

The canonical schema is
[`../Employee Management Tool.postgres.sql`](../Employee%20Management%20Tool.postgres.sql)
(PostgreSQL). Everything lives in **one central database**, shared with the
identity service.

### Org-domain tables (owned by this service)

| Table | Key columns | Notes |
|---|---|---|
| `Tenant` | `TenantId` (PK, identity), `Uid` (public UUID) | Top-level tenant. |
| `Organization` | `OrganizationId` (PK), `TenantId` → `Tenant` | An org belongs to a tenant. |
| `Department` | `DepartmentId` (PK, uuid), `OrganizationId` → `Organization` | Reaches its tenant via `Organization` — no redundant `TenantId`. |
| `DomainUser` | `DomainUserId` (PK, uuid), `TenantId` → `Tenant`, `IdentityUserId` (unique) | The domain "person" — **distinct from the Identity `ApplicationUser`**. `IdentityUserId` links to Identity `AspNetUsers.Id`. `IsActive` = account/login state. |
| `Employee` | `EmployeeId` (PK), `DomainUserId` → `DomainUser` (unique), `DepartmentId` → `Department` | The HR record for **everyone in a department, managers included**: job title, hire/end date, salary. One per person. `EmploymentStatus` ∈ {`Active`, `Inactive`}; `EndDate` null while employed. |
| `Manager` | `ManagerId` (PK), `EmployeeId` → `Employee` (unique), `DomainUserId` (unique), `DepartmentId` | A **manager designation on an existing employee**. `DomainUserId`/`DepartmentId` are redundant copies of the employee's, kept for existing queries — see below. |
| `ReportingLine` | `ReportId` (PK) → `DomainUser`, `ManagerId` → `Manager` | The org chart (see below). |

### Managers are employees

A manager is promoted from an existing `Employee`; there's no separate HR record for
managers. `Manager` points at that employee with `EmployeeId`, and keeps
`DomainUserId` and `DepartmentId` as redundant copies so `Department.Managers` and
the existing manager queries still work.

The database keeps the copies honest. `FK_Manager_Employee` is a **composite** foreign key:

```sql
FOREIGN KEY ("EmployeeId", "DomainUserId", "DepartmentId")
  REFERENCES "Employee" ("EmployeeId", "DomainUserId", "DepartmentId")
  ON UPDATE CASCADE
```

- A `Manager` row can only exist with the **same person and department** as its
  `Employee` row (so a person can't be an employee in one department and a manager
  in another).
- Moving the employee to another department moves their `Manager` row with it.
- `Employee` carries `UQ_Employee_DomainUserId` (one HR record per person) and
  `UQ_Employee_Id_User_Dept` (the key the composite FK references).

Rules enforced in code:

- `add-manager` takes only `{ employeeId }`; the service copies the person and
  department from that employee and rejects anyone who's already a manager.
- There's no edit-manager endpoint: department changes go through `edit-employee`
  and cascade.
- `DomainUser.Role` follows the highest designation — `employee` when an employee is
  created, `manager` when promoted, back to `employee` when the manager designation
  is deleted. `sys-admin` and `company-admin` are never overwritten.
- Responses list a person once: `get-department-info` leaves managers out of
  `employees`, manager responses carry the HR fields from the linked `Employee`, and
  employee responses carry `managerId` when the employee is also a manager.

### Reporting lines

`ReportingLine` unifies the whole org chart in one table:

- `ReportId → DomainUser` — the subordinate (an IC's *or* a manager's user).
- `ManagerId → Manager` — the boss, always a designated manager.

This replaces the older `Employee.ManagerId` / `Manager.SupervisorId` FK columns,
so both chains — IC → manager and manager → supervisor — live in one place. The
PK on `ReportId` enforces **one manager per person**; widen to a composite PK
`(ReportId, ManagerId)` to allow matrix/dotted-line reporting.

### Identity / auth (shared DB, owned by the identity service)

- ASP.NET Core Identity tables (`AspNetUsers`, `AspNetRoles`, …) are generated by
  EF Core migrations, not the SQL script. `ApplicationUser.Id` is the canonical
  user id across the platform (the JWT subject). Don't confuse `ApplicationUser`
  (the Identity / auth user) with `DomainUser` (the org person) — they're linked by
  `DomainUser.IdentityUserId`.
- `RefreshToken` (`Token`, `IdentityUserId`, `ExpiresAt`, `IsRevoked`, `IsUsed`).
  `IsExpired`/`IsActive` are computed in code, not stored.

### Off-boarding (soft delete)

Leavers are **soft-deleted, never hard-deleted**: set `Employee.EmploymentStatus
= 'Inactive'` + `EndDate`, flip `DomainUser.IsActive = false`, revoke refresh tokens,
and reassign the leaver's reports in `ReportingLine`. Rows stay for history and to
keep FKs valid.

## API authorization

JWT bearer only: the identity service issues tokens, this service validates them
(`JwtBearer` middleware) and enforces role-based policies. Each `DomainUser` has one
role — `sys-admin`, `company-admin`, `manager`, or `employee` — emitted as a `role`
claim. Policies are registered in
[`Program.cs`](Employee.Management.Api/Program.cs) and applied at the controller
level with `[Authorize(Policy = …)]`:

| Policy | Roles allowed | Controller (route) |
|---|---|---|
| `SystemAdmin` | `sys-admin` | `SysController` (`sys-api`) — cross-tenant platform admin |
| `CompanyPermission` | `sys-admin`, `company-admin` | `AdminController` (`company-admin-api`) |
| `ManagerPermission` | `sys-admin`, `manager` | report tier (per endpoint) |
| `EmployeePermission` | `sys-admin`, `employee`, `manager` | report tier (per endpoint) — a manager is also an employee |

`sys-admin` appears in **every** policy, so it is a superuser — system-only
endpoints *plus* every lower tier (a role-hierarchy model). Still open: whether
`sys-admin` should also bypass future per-tenant ownership checks, or reach a
tenant's business data only through dedicated, audited endpoints.

**The report tier is provisional.** `ReportController` (`report-line-api`) carries
`[Authorize(Policy = "ReportUser")]`, but no `ReportUser` policy is registered yet;
it's an empty shell, so nothing throws. When endpoints land, scope them per role on
the single controller rather than splitting it — stacked `[Authorize]` attributes
combine with **AND**, so a broad controller baseline can be *narrowed* per action
(widening across roles needs one multi-role policy). `UserController` (`api/User`)
is authentication-only (`[Authorize]`) for now.

## Known limitations / TODO

### Reporting lines (`ReportingLine`) — deferred validation

The org chart is stored in the `ReportingLine` table (`ReportId -> DomainUser`,
`ManagerId -> Manager`). The database enforces the hard invariants: one manager
per person (PK on `ReportId`) and valid references (FKs). Two business rules are
**not yet enforced** and are deliberately deferred while this is a demo:

- **Self-reporting** — nothing stops a person from reporting to themselves
  (`ReportId`'s user == `ManagerId`'s user). The DB can't express this with a
  simple `CHECK` because the two columns reference different tables. Add a guard
  in the reporting-line write path before production.
- **Cycles** — A reports to B who reports back to A (or a longer loop). This
  can't be caught by a constraint at all; it needs a graph walk. Validate the
  whole resulting chain (recursive check) before inserting an edge.

Until these exist, code that walks the org chart should not assume the graph is
acyclic. If matrix/dotted-line reporting is ever needed, widen the PK to
`(ReportId, ManagerId)`.
